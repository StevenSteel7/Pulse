# Pulse (macOS app + widget)

A SwiftUI menu-bar app and Sonoma-style desktop widget that shows live CPU,
RAM, GPU, and disk stats from your Windows PC and Linux/Oracle VPS. Compact
**PC / VPS** buttons switch systems directly on the widget without opening
the app. Companion agents: `../windows-agent/` and [Linux installer](linux-agent/README.md).

For one-command GitHub installation, see [GITHUB-INSTALL.md](GITHUB-INSTALL.md).

## Project layout

```
macos-app/
  project.yml              <- xcodegen spec (source of truth for the project)
  Pulse.xcodeproj           <- generated by xcodegen, already checked in
  Pulse/                    <- main app target (window + menu bar extra)
  PulseWidget/              <- widget extension target
  Shared/                   <- models, networking, shared-file storage, UI
                               pieces used by BOTH targets
```

`Pulse.xcodeproj` was generated with [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from `project.yml`. You don't need XcodeGen to open and run the project —
just open `Pulse.xcodeproj`. You only need XcodeGen again if you add/rename
files or change target settings and want to regenerate the project file
(`brew install xcodegen && xcodegen generate`).

## Opening it for the first time

1. `open Pulse.xcodeproj`
2. Select the **Pulse** project in the navigator → each target (**Pulse**,
   **PulseWidgetExtension**) → **Signing & Capabilities** and confirm both
   targets use the same **Team**. The project is currently configured for
   team `ZX4J42CV74`; if you use another account, change `DEVELOPMENT_TEAM`
   in `project.yml` and regenerate the project. The shared App Group is
   derived from that value as
   `$(DEVELOPMENT_TEAM).com.stevensteel.pulse`.
3. Select the **Pulse** scheme → Run. Pulse stays in the menu bar. Choose
   **Advanced** to open the dashboard, then the gear to configure your systems.
   Existing Windows credentials migrate to the PC profile. Add the Linux
   agent's connection details under **Oracle VPS** and save.
4. Add the widget from desktop → Edit Widgets → **Pulse**, choosing a size.
   Use its **PC / VPS** buttons to switch the shared active system. The menu
   bar and dashboard also have system selectors. Readings and history are
   cached separately by system and endpoint; unavailable systems show their
   own last readings or an empty state, never the other system's data.
5. For your Oracle VPS, follow the [single-script Linux setup](linux-agent/README.md).

## Building a .dmg

Once you've got Pulse running from Xcode with signing sorted out (see above),
package it for normal drag-to-/Applications installation instead of running
it from Xcode every time:

```bash
./build_dmg.sh
```

This does a clean Release build of the `Pulse` scheme (app + widget
extension embedded), then packages `Pulse.app` into `dist/Pulse.dmg` — using
[`create-dmg`](https://github.com/create-dmg/create-dmg) for a nicer
drag-to-Applications layout if you have it (`brew install create-dmg`), or
falling back to plain `hdiutil` (always available) if you don't.

Requires **full Xcode.app**, not just the Command Line Tools (this sandbox's
environment only has the latter, which is why this script couldn't be
verified by actually running it here — review it before trusting it blindly
on a machine you care about, though it's a straightforward `xcodebuild` +
`hdiutil` wrapper).

If your Xcode-configured Team ever gets reset (e.g. after re-running
`xcodegen generate`, since `project.yml`'s `DEVELOPMENT_TEAM` is intentionally
blank), pass your Team ID explicitly:

```bash
./build_dmg.sh ABCDE12345
```

(Find your Team ID in Xcode → Settings → Accounts → your Apple ID → team
list, or on developer.apple.com/account under Membership.)

### A note on Gatekeeper

Signing here uses your personal/free "Apple Development" certificate (visible
as automatic signing in Xcode), not a paid "Developer ID Application"
certificate. That's fine for installing and running the .dmg **on the same
Mac you built it on** — a locally-created file has no quarantine flag, so
Gatekeeper doesn't even check it.

It will **not** pass Gatekeeper on a different Mac (or if the .dmg picks up
a quarantine flag from being downloaded/AirDropped/emailed) — you'd see
"Apple could not verify this app is free of malware." For personal use on
your own machine that's not a concern. If you ever want to share it with
someone else's Mac:
- quick workaround: right-click the app → Open (bypasses Gatekeeper once),
  or strip the flag with `xattr -cr /Applications/Pulse.app`
- proper fix: enroll in the paid Apple Developer Program, sign with a
  "Developer ID Application" certificate, and notarize with
  `xcrun notarytool submit` + `xcrun stapler staple` — a bigger step this
  project doesn't set up automatically since it requires a paid account.

## How the pieces fit together

- **Pulse (main app target)** — SwiftUI window (`DashboardView`) plus a
  `MenuBarExtra`. `PulseMonitor` polls `GET /stats` every 5 seconds *while
  the app process is running* and publishes the result to the UI.
- **Shared/** — `StatsClient` (the actual HTTP fetch), `StatsModels` (mirrors
  the agent's JSON), `SettingsStore`/`SharedStore` (both backed by a plain
  JSON file in the shared App Group container, see `SharedContainer.swift`),
  and reusable SwiftUI pieces (`PulseRing`,
  `PulseBar`, `StatusPill`) so the app and widget look like one coherent
  design system.
- **PulseWidget (widget extension target)** — `PulseTimelineProvider` does
  its own independent fetch each time WidgetKit calls it, caches the result
  into the same shared file, and falls back to the last cached value
  (marked "Offline") if the fetch fails.

Every successful poll — from either the app or the widget — writes into the
selected system’s shared cache file and (from the app) calls
`WidgetCenter.shared.reloadTimelines(ofKind: "PulseWidget")`. That's what
keeps the widget's *displayed* value close to real-time even though its own
`getTimeline` calls are infrequent — see below.

### Why the App Group starts with the Team ID

WidgetKit requires the widget extension to have the App Sandbox entitlement,
so it cannot read the main app's ordinary
`~/Library/Application Support/Pulse/` directory. Both targets therefore
share settings and snapshots through an App Group container.

On macOS, an App Group identifier must start with the signing Team ID. The
older `group.com.stevensteel.pulse` identifier was rejected by
`containermanagerd`, leaving the widget with default settings and no cache.
This project now uses
`$(DEVELOPMENT_TEAM).com.stevensteel.pulse` for both targets and enables
outgoing network access on the sandboxed widget. Existing settings are migrated from the old Application Support location when
the updated main app first launches. Old snapshots have no system identity,
so they are replaced with fresh per-system caches.

## Refresh-rate reality check (read this before expecting 1-second updates)

WidgetKit widgets are **not** allowed to run their own polling loop in the
background. The system calls your `TimelineProvider.getTimeline` on a
budget it controls — roughly a handful of times per hour for a widget
belonging to an app the user isn't actively using, more if the app is
frequently opened, `WidgetCenter.reloadTimelines` is called, or the widget
is currently visible in an active Space. There is no API to ask for
"refresh every 5 seconds" and have the system honor it — it will just
throttle you.

Given that hard constraint, this project's approach is:

1. **The widget's own timeline** requests a reload every 15 minutes
   (`PulseWidget.swift`), which is realistic and won't get silently dropped
   for being too aggressive.
2. **The menu bar app is the actual near-live path.** `PulseMonitor` polls
   every 5 seconds whenever Pulse.app is running (foreground apps aren't
   subject to the widget budget), writes into the shared App Group cache,
   and nudges `WidgetCenter.reloadTimelines`. macOS still decides *when* to
   actually redraw the widget from that nudge, but in practice, with the
   app running (e.g. launched at login), the widget updates far more
   often than its own 15-minute timeline would alone — commonly every
   1–5 minutes, sometimes faster right after you click on the widget or
   switch Spaces, since that's when the system is more willing to spend
   budget.
3. **If you close Pulse.app entirely**, the widget still works — it just
   falls back to its own ~15-minute cadence.

If you want it running automatically: System Settings → General → Login
Items → add Pulse.app. Since it's already a small, lightweight menu bar
resident, there's no separate helper binary to install — it *is* the helper.

There is no way to get true 1-second widget refresh on macOS short of
Apple changing WidgetKit's refresh budget policy. If you need second-level
precision, use the menu bar dropdown or the main window, which show
`PulseMonitor`'s 5-second-polled values directly (not the widget).

## Handling SIXDX being asleep/off/unreachable

- `StatsClient.fetch` uses a short timeout (3s from the app, 4s from the
  widget) so a dead connection never hangs the UI.
- On failure, the app keeps showing the last known stats with the status
  pill flipped to **Offline** rather than blanking the screen.
- The widget does the same, using whichever cached snapshot is freshest
  (its own or one written more recently by the running app), and shows
  "Last seen Xm ago" instead of "Updated Xm ago".
- If nothing has ever been fetched (fresh install, no config yet), both
  show an explicit "not configured / no data" state — never a spinner that
  hangs forever.

## Security note on the API key

The API key is stored in plain text in the shared App Group's
`settings.json`. For a LAN shared secret used only by your own two targets,
that's a reasonable tradeoff. If stronger protection is needed, move it to
a Keychain item with a keychain access group shared by both targets.
